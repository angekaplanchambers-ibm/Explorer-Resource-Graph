Terraform Control CenterPositioningAn intent layer for Terraform operations � starting as a global command bar, expanding into guided workflows when the task requires context, decisions, approvals, or evidence.Terraform Control Center should not present itself as a chatbot or a human-like assistant. It should feel like a precise, technical control surface inside HCP Terraform / Terraform Cloud: searchable, inspectable, deterministic, permission-aware, and fully reviewable. Meridian provides the orchestration patterns � intent capture, target binding, guardrails, plan/review/approve, simulation, artifacts, audit, and recovery � while the user-facing experience remains native to Terraform.Core design stanceThe experience should be dehumanized by design. Trust should come from machine-state clarity, not conversational personality.Use machine-state language* Pulling workspace data.* Checking policy results.* Generating proposed plan.* Comparing current and proposed state.* Approval required.* 3 blocking issues detected.Avoid human-like language* �I�m pulling workspace data for you.�* �I think you should approve this change.�* �Let me check that.�* �Great, I found something.�The user should feel in control of an operational system � not at the mercy of a conversational agent.The interface should communicate state, constraints, evidence, and next valid actions. It should avoid avatars, typing indicators, emotional reassurance, assistant metaphors, or performative reasoning. Terraform users already trust systems that expose plans, diffs, state, policy checks, approvals, and applies. Terraform Control Center should extend that trust model.Product conceptTerraform Control Center begins as a global entry point available throughout HCP Terraform / TFC. A user can invoke it from anywhere and enter intent in natural language or structured terms:* Find failed production runs* Inspect drift in payments workspaces* Prepare provider upgrade for AWS workspaces* Create workspace for new service* Explain this policy failure* Generate approval evidence for this runThe surface initially behaves like a technical command/search interface. It returns structured results � not chat bubbles � such as workspaces, runs, plans, policies, modules, docs, workflows, actions, artifacts, and sessions. When the request is simple, the experience stays lightweight. When the request carries operational risk or requires judgment, the interface expands into a guided workflow.Interaction model: progressive escalation1. Find � navigation and lookup. Example: �production workspaces with failed runs� returns a filtered workspace list.2. Inspect � lightweight understanding. Example: �why did this run fail� returns the failed phase, blocking policy, cost delta, and available next actions.3. Prepare � context binding and recommendations. Example: �prepare drift remediation for production� binds target workspaces, detects drift, groups affected resources, and generates a remediation packet.4. Execute � mutating workflows requiring approval, checks, and traceability. Example: �upgrade AWS provider across production� creates a durable session with compatibility analysis, plan generation, policy checks, approval, execution, verification, and audit export.HCP Terraform / TFC surfacesGlobal control barThe first visible entry point, collapsed at the bottom of the screen and expandable. It persists across all Terraform pages, anchored to the bottom and therefore accessible at any given point. The feature name �Terraform Control Center� would be shown (think AWS CloudShell). In the collapsed and expanded view placeholder text is shown to give insight to users what the feature is for. Recommended placeholder:Search, inspect, or prepare infrastructure changes�Avoid �Ask AI,� �Chat with Terraform,� �Tell Meridian,� or �How can I help?� The bar should feel like a product control, not a conversation.Contextual entry pointsSmall actions embedded in existing Terraform surfaces:* Failed run: Inspect failure* Policy failure: Prepare exception packet* Drift detection: Prepare remediation* Workspace: Review workspace health* Provider version: Plan upgrade* Apply: Export evidenceGuided workflow workbenchWhen a task requires structure, Terraform Control Center opens a workbench showing current step, bound target, selected guardrails, generated plan, policy status, required approvals, artifacts, audit status, and next valid actions.* Target bound* Input required* Plan generated* Policy check failed* Approval required* Run queued* Apply completed* Evidence exportedSessions and auditComplex work becomes a durable session: a container for an infrastructure outcome. A session may include multiple plans, runs, policy checks, generated PRs, approvals, artifacts, and verification steps.* Session: Drift remediation � production networking* Session: AWS provider upgrade � payments* Session: Workspace creation � inventory service* Session: Policy exception packet � cost thresholdThe audit layer should make it clear what was requested, what targets were bound, what decisions were made, what checks ran, what changed, who approved, what artifacts were produced, what failed or required intervention, and what evidence was exported.Why this worksTerraform Control Center keeps the experience technical, controllable, and native to Terraform. Users can express outcomes, but every meaningful operation is translated into visible Terraform structures: intent ? target ? plan ? checks ? approval ? execution ? verification ? evidence.This is the bridge from Meridian to HCP Terraform / TFC: not a chatbot, not a new shell, and not an autonomous black box � but a technical intent layer that makes Terraform operations faster, safer, more inspectable, and more controllable.Source contextThis one-pager is based on the provided Meridian / HCP Terraform / Enterprise OS designer guide and the Meridian demo transcript/screenshots shared in the conversation.
