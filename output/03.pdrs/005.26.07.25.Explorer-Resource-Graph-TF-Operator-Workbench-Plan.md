## Overview

The Agentic TFC prototype (`030.Agentic_TFC`) demonstrates a proven three-layer wiring model for the Workspaces view:

```
WorkspacesView
  └── signal banners with onControlCenterTrigger
        └── ControlCenter (bar → macro panel → TriagePanel with evidence + next steps)
              └── Workbench (full-screen, query-bound, step-by-step confirmation chain)
```

This plan ports that same interaction model to the **Explorer View** surface. Explorer is not a copy of Workspaces — it is a different data surface with different signal types. But the wiring architecture is identical:
- Explorer's table rows and signal banners trigger the ControlCenter with pre-bound queries
- ControlCenter's TriagePanel surfaces evidence from resource catalog data and offers next steps into Workbench
- Workbench handles deep investigation: dependency traversal, blast-radius analysis, resource inspection, and preparation of remediation packets

The result: **Explorer becomes the intelligence entry point for infrastructure-level agent work, using the same verified intent loop already proven in the Workspaces surface.**

**What this plan does not change:**
- Explorer's table-first design: the table remains primary, the ControlCenter is additive
- Explorer's existing type cards, use cases, saved views, or query builder
- The Workbench internals — only new `pageContext` handling and new Explorer-specific `LANDING_WORKFLOWS` and `CONTEXT_HINTS` are needed
- ETL or conversational query service implementation (separate workstreams)

### Sub-Task 1: Add signal banners to the Explorer resource table

**Status**: [ ] pending

**Intent**
The Workspaces view's most powerful agentic entry point is not a chat drawer — it is the contextual signal banner. When 3 workspaces have failed runs, a red banner says "3 workspaces have failed runs — last 60 minutes" and offers "Inspect failures" as an immediate action. The user never has to construct a query.

Explorer needs the same pattern. When the resource catalog contains signals — resources with drift, resources in failed workspaces, resources missing from expected state, provider upgrades available — the table should surface those signals as dismissible banners at the top of the result set, each with a single pre-bound action that triggers the ControlCenter.

**Expected Outcomes**
- The Explorer resource result page (when showing Resources type) renders signal banners above the table when the catalog returns signal data
- Each banner follows the Agentic TFC model: icon + message + single `Zap` action button
- Clicking the action button calls `onControlCenterTrigger(pre-bound query)` — the ControlCenter opens pre-loaded
- Banners are dismissible and do not block the table
- Signal types for the first slice: resources in failed workspaces, drift-detected resources, provider upgrade available

**Todo List**

   - Failed workspace signal: "N resources in workspaces with failed runs" → action: "Inspect resources"
   - Drift signal: "N resources with drift detected" → action: "Prepare remediation"
   - Provider signal: "Provider upgrade available for N resources" → action: "Plan upgrade"
2. Specify the banner visual treatment: follow Agentic TFC exactly — red/amber/blue background tint, border, icon, message, Zap button
3. Specify the pre-bound query that each banner action passes to `onControlCenterTrigger`
4. Specify dismissal behavior: banner disappears for the session; does not re-appear unless data changes
5. Specify the empty banner state: if no signals, no banners (table renders at full height)

**Relevant Context**

### Sub-Task 2: Add contextual Zap triggers to Explorer resource table rows

**Status**: [ ] pending

**Intent**
The Workspaces table has per-row contextual action buttons: failed rows show "Inspect failure", drifted rows show "Prepare remediation". These are not menu items — they are inline Zap buttons that appear only when the row's status warrants them. They pre-bind the row's name to the ControlCenter query.

Explorer's resource table needs the same pattern. A resource row showing a failed workspace status should offer "Inspect failure". A resource row with a `dependency_reason` annotation should offer "Show blast radius". A resource row in a workspace with a provider upgrade signal should offer "Plan upgrade".

**Expected Outcomes**
- Resource rows in the Explorer table render an inline action area in the last column (matching Agentic TFC pattern)
- Failed workspace rows: "Inspect failure" `Zap` button → `onControlCenterTrigger("Inspect failure: {workspace_name}")`
- Resources with drift: "Prepare remediation" → `onControlCenterTrigger("Prepare drift remediation for {workspace_name}")`
- Resources with known downstream dependents: "Show blast radius" → `onControlCenterTrigger("Show blast radius of {resource_address} in {workspace_name}")`
- A `MoreHorizontal` menu button always present (matches Agentic TFC pattern) for other row-level actions
- Buttons only appear when the row's data warrants them — not as permanent UI

**Todo List**
1. Define the full set of row-level signal conditions and their corresponding trigger labels and queries:
   - `workspace.status === "failed"` → "Inspect failure"
   - `workspace.driftDetected === true` → "Prepare remediation"
   - `resource.dependents.length > 0` → "Show blast radius"
   - `workspace.providerUpgradeAvailable === true` → "Plan upgrade"
2. Specify the button visual treatment: follow Agentic TFC exactly (Zap icon, small px/py, border, tinted background matching signal color)
3. Specify the query string format for each trigger so ControlCenter's `OPS_BY_PAGE["explorer"]` can pattern-match it
4. Specify the column layout: last column contains the action area; cells without signals show only `MoreHorizontal`

**Relevant Context**
- Agentic TFC reference: [`WorkspacesView.tsx`](../01.meetings/030.Agentic_TFC/src/app/components/WorkspacesView.tsx) lines 413-440 — the per-row inline action area
- `e.stopPropagation()` on the Zap button click is critical — row is clickable for expand; the Zap should not propagate to the row expand
- "Show blast radius" is the Explorer-native trigger that Workspaces does not have — this is the new capability Explorer uniquely contributes

## Constraints

- **Table stays primary.** The ControlCenter is additive. If a user ignores every banner and Zap button, Explorer is fully functional.
- **Workbench is full-screen.** No co-rendered Workbench alongside Explorer table. The Agentic TFC slide-up pattern is the correct model.
- **D3 is prohibited.** The `InfragraphTab` in Workbench uses SVG-only rendering. Explorer scenarios must not introduce D3.
- **No new Workbench UI patterns.** Explorer scenarios use the same `Message` types already in Workbench: `finding`, `table`, `confirm`, `codeDiff`. No new card types.
- **Solace real estate.** ControlCenter must not conflict with a potential Solace right panel. The `icon-only` collapse rule from the Explorer upgrade plan applies.
- **`pageContext` string is the integration key.** Everything flows from `pageContext="explorer"` — ControlCenter op selection, Workbench hints, Workbench right-panel tab, and scenario routing all key off this string.
