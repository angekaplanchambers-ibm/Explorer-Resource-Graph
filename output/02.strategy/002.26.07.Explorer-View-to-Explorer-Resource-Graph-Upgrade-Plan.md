## Overview

This plan sequences the design work to take Explorer View from its current state to what the design notes describe as Explorer Resource Graph. The upgrade is additive — nothing in Explorer View is removed. New capabilities are layered on top of the proven metadata-table foundation.

**The upgrade has three layers, each building on the last:**

1. **Data layer** — richer data behind the existing table (resource attributes, dependency closure, cross-workspace edges). No UI change yet. Required for everything that follows.
2. **Table layer** — new query types, new pre-built use cases, and a `Resources` type card that exposes the new data through the existing Explorer interaction model.
3. **AI + graph layer** — conversational query drawer at the bottom and a supplemental graph view that the LLM can manipulate. Table stays primary; graph and chat are additive.

**What is not in scope for this plan:**
- ETL service architecture implementation (owned by TF-2038, Alex Redinger's team)
- Conversational query service implementation (owned by TF Partner Integrations, Nicole Mak design)
- Graph visualization library selection (D3 ruled out — library TBD with engineering)
- Solace integration specifics (depends on Solace roadmap confirmation)
- InfraGraph feature parity or InfraGraph migration

### Sub-Task 1: Add `Resources` as a fifth Type in the existing TYPES_SECTION

**Status**: [ ] pending

**Intent**
Explorer View's TYPES_SECTION currently has four type cards: Modules, Providers, Workspaces, Terraform Versions. The new data layer (resource instances with full JSONB attributes and dependency closure) needs a surface. The smallest valid UI change is adding `Resources` as a fifth card in the existing row — no layout changes, no new pages needed outside what Explorer already has for type drill-down.

This is the design prerequisite for all subsequent work. It gives the data layer a home before any conversational or graph capability is added.

**Expected Outcomes**
- A `Resources` type card appears in the TYPES_SECTION alongside the existing four cards
- Clicking it routes to `/app/{org}/explorer/types/Resources?type=resources`
- The resources result page renders resource instances in the existing tabular format, with columns: workspace, address, resource type, resource name, module, provider, instance key
- Attribute values are surfaced in an expandable row or detail panel — not a separate page
- The card is present in the sidebar navigation link structure and breadcrumb

**Todo List**
1. Define the `Resources` type card spec: icon, label, aria-label, route, query params
2. Specify the resources result table column set (workspace, address, type, name, module, provider, instance key)
3. Specify the attribute expansion pattern: expandable row panel showing JSONB attributes, with `<sensitive>` values rendered as a muted placeholder, not hidden
4. Specify filter parameters available on the resources result page: `workspace_id`, `resource_type`, `org_id`, `project_id`, `attr[key]=value` (exact match)
5. Add resource-specific pre-built use cases to USE_CASES_SECTION (see Sub-Task 2)
6. Update the Explorer page reference doc (`hcp-tf-ui-for-agents/pages/explorer.md`) with the new type card, routes, and patterns

**Relevant Context**
- Current TYPES_SECTION pattern: `Icon + label + arrow` card routing to `/app/{org}/explorer/types/{Name}?type={type}`
- Resource attribute values from the catalog are JSONB with sensitive values already replaced by `"<sensitive>"` at ingest — no additional sanitization needed in the UI
- The `Resources` type is backed by the `resource_instances` table (see Graph Catalog schema in [`022.26.07.15.Terraform-Graph-Catalog-PoC-Synthesis.md`](../01.meetings/022.26.07.15.Terraform-Graph-Catalog-PoC-Synthesis.md))
- Page must support keyset pagination (cursor-based) — not offset pagination — to handle 2M+ resources at scale

### Sub-Task 2: Add resource-focused pre-built use cases to USE_CASES_SECTION

**Status**: [ ] pending

**Intent**
The existing USE_CASES_SECTION has 12 use cases covering workspaces, modules, providers, and TF versions — none covering resource instances. Adding resource-focused pre-built use cases directly into the existing card grid is the fastest way to surface new data value without any structural UI change.

These use cases answer the questions customers have been asking for years that Explorer cannot currently answer.

**Expected Outcomes**
- At least five new use-case cards appear in USE_CASES_SECTION under a `Resources` grouping or interleaved with existing cards
- Each card routes to a pre-filtered resources result page
- Cards follow the existing `Icon + label + arrow` pattern

**Todo List**
1. Define the initial five resource use-case cards (see candidate list below)
2. Specify the pre-configured query params for each card's route
3. Confirm the card visual grouping strategy: add a "Resources" label heading above the new cards, or interleave with existing cards by relevance
4. Specify the empty state for each use case (e.g. "No EC2 instances found across your workspaces")

**Candidate use-case cards (first five, validate with PM):**
- "EC2 instances by type" — filter: `resource_type=aws_instance`, attribute sort by `instance_type`
- "All S3 buckets" — filter: `resource_type=aws_s3_bucket`
- "Resources by provider version" — cross-reference `resource_instances` with `workspace_providers` by workspace
- "Resources with sensitive attributes" — filter showing which resource types have `<sensitive>` placeholder values (governance signal)
- "Largest workspaces by resource count" — workspace summary sorted by `resource_count` descending

**Relevant Context**
- Existing use-case pattern is pre-configured query params appended to `/app/{org}/explorer/types/{name}?...`
- The LLM system prompt (from Graph Catalog) shows the range of questions users will ask — the pre-built cards should answer the most common ones so users don't need to write queries manually
- "Resources with sensitive attributes" is a governance use case that maps directly to the Security & Compliance Operator persona in the PRD

### Sub-Task 3: Add dependency context to the resource detail view

**Status**: [ ] pending

**Intent**
Once resource instances are queryable (Sub-Task 1), the next most valuable addition is showing what a resource depends on and what depends on it — within the same table-first interaction model. This is the "blast radius in miniature": scoped to one resource, not the full cross-workspace analysis.

This does not add a graph view yet. It adds a `Dependencies` and `Dependents` section to the resource detail panel, using the existing expandable row pattern.

**Expected Outcomes**
- The resource detail panel (expanded row from Sub-Task 1) gains a `Dependencies` section listing the resource addresses this resource depends on
- The panel gains a `Dependents` section listing resource addresses that depend on this resource, each annotated with `dependency_reason` (explicit / implicit:attribute / unknown)
- Each dependency address is a link that navigates to that resource's detail in the same Explorer view
- The dependency list is paginated if more than 20 items

**Todo List**
1. Specify the `Dependencies` section layout within the expanded row panel: heading, list of addresses with their `resource_type`, `workspace_id`, and a `dependency_reason` badge
2. Specify the `Dependents` section layout: same structure plus the `dependency_reason` annotation from the `GetDependents` API
3. Specify the link-out behavior: clicking a dependency address filters the resources table to that address in its workspace — context preserved
4. Specify the empty state for each section: "No dependencies recorded" / "No dependents found"
5. Specify the pagination affordance for long dependency lists (show first 20, "Show N more" expander)
6. Determine whether `dependency_reason: unknown` items display differently from `explicit` and `implicit:attribute` — recommendation: show all, but label `unknown` with a muted style and tooltip explaining it means config data was not available at ingest

**Relevant Context**
- `dependency_reason` values come from the `GetDependents` query in the Graph Catalog: `explicit` (declared `depends_on`), `implicit:<attribute>` (expression reference), `unknown` (config not ingested or transitive only)
- The dependency closure in `resource_instances.dependencies` is the full transitive set — the UI should show it but make clear these are transitive, not just direct
- This is the within-workspace dependency view. Cross-workspace blast radius is Sub-Task 5.

### Sub-Task 4: Conversational query drawer (bottom entry point)

**Status**: [ ] pending

**Intent**
The conversational query feature is owned by TF Partner Integrations (Nicole Mak, design), but the placement and interaction contract with Explorer View must be specified here. This sub-task defines the drawer: where it lives, how it opens, what it shows, and how it interacts with the existing Explorer table.

The drawer is **not a chat panel**. It is a call-and-response experience: user asks a question, agent responds with an answer grounded in infrastructure data, and the answer updates or filters the Explorer table view. The drawer does not replace the table — it drives it.

**Expected Outcomes**
- A persistent collapsed affordance at the bottom of the Explorer page: a narrow bar labeled "Ask about your infrastructure" with an expand chevron
- Expanding it reveals a single input field and a suggestion strip of starting questions (e.g. "How many EC2 instances do I have?", "What depends on workspace payments-prod?", "Show blast radius of ws-network-prod")
- Submitting a question triggers a response: the agent returns a text answer + a set of table filter parameters
- The Explorer table automatically updates to show the results of the query
- A transparency strip below the agent's answer shows which catalog tools were called (e.g. "Queried: list_resources, get_blast_radius")
- The drawer retains the conversation history for the session

**Todo List**
1. Specify the collapsed state: bottom bar height, label text, expand affordance, visual treatment (border, background, z-index relative to footer)
2. Specify the expanded state: input field, suggestion strip (3-5 static suggested questions), submit button, loading state
3. Specify the response rendering: text answer in markdown-lite (bold, inline code, short lists), transparency strip showing tool calls
4. Specify the table integration contract: the agent response includes a structured filter payload that the Explorer table applies (workspace_id, resource_type, attr_filters) — define this payload shape
5. Specify the "reset filters" affordance: after an agent-driven filter is applied, a dismissible chip appears above the table ("Filtered by: EC2 instances in org/payments — Clear")
6. Specify the bottom drawer real estate rules for Solace coexistence: drawer sits above the page footer; if Solace right panel is open, drawer collapses to icon-only mode in the bottom-left
7. Specify the empty / error states: no results, agent could not answer, LLM service unavailable

**Relevant Context**
- Ange confirmed bottom drawer placement in the Chris 1:1: "that's going to be something that will probably exist along the bottom instead of the side panel because if we're integrating Solace as well, like that takes up the right real estate"
- The LLM chat system prompt from the Graph Catalog defines exactly how the agent interprets queries and which tools it calls — this is the backend contract the drawer must assume
- The drawer is UI-agnostic at the service level (TF Partner Integrations builds it as a standalone service) — Explorer View is the first surface it appears on
- Suggested starting questions should map to the pre-built use cases from Sub-Task 2 so users see continuity between the card-based and conversational entry points

### Sub-Task 5: Graph view as supplemental context panel

**Status**: [ ] pending

**Intent**
The graph visualization is the lowest-priority addition and must not become the primary experience. Its role is the "minimap": it provides macro-level orientation after a user has found something of interest in the table.

This sub-task specifies the graph panel as a secondary view that can be toggled alongside the table, and that the conversational agent (Sub-Task 4) can manipulate (highlight a workspace, enter blast-radius mode, switch views).

The graph is not a standalone page. It is a panel.

**Expected Outcomes**
- A `Graph` toggle button appears in the Explorer toolbar alongside the existing display controls
- Activating it opens a side-by-side or stacked panel: table on the primary side, graph on the secondary side
- The graph defaults to the **Workspaces view**: nodes are workspaces, edges are cross-workspace `terraform_remote_state` dependencies
- Selecting a workspace node in the graph filters the table to resources in that workspace
- Selecting a resource row in the table highlights the owning workspace node in the graph
- The conversational agent can call UI-action tools to manipulate the graph: `focus_workspace`, `show_blast_radius`, `navigate_view`
- The graph visualization library is **not D3** — library selection is a joint decision with engineering (placeholder in this spec)

**Todo List**
1. Specify the toggle affordance: button label ("Show graph" / "Hide graph"), placement in the toolbar (right side, after display/layout controls)
2. Specify the three graph views and their tab labels: Workspaces (cross-workspace dependency graph), Resources (DAG of resources within a selected workspace), Providers (bipartite: providers ↔ workspaces)
3. Specify the layout split: default 60/40 table/graph; user-resizable; graph can be hidden (returns to 100% table)
4. Specify the bidirectional selection behavior: workspace node click → table filter; resource row click → workspace highlight
5. Specify the blast-radius visual mode triggered by the agent (`show_blast_radius`): dims unrelated nodes, paints downstream consumers with a hop-distance color gradient (1 hop = lightest, 3+ hops = darkest)
6. Specify the three layout algorithms for the graph: force (default), stacked, radial — user-selectable from a segmented control in the graph panel toolbar
7. Specify what the graph does on empty or low-data states: if fewer than 2 workspaces have edges, show a message "Not enough cross-workspace connections to visualize — add `terraform_remote_state` data sources to see dependencies"
8. Document the library constraint: D3 is prohibited (security policy). Propose two alternatives for engineering evaluation (e.g. Cytoscape.js, vis-network) and flag for joint decision

**Relevant Context**
- Chris Arcand's minimap framing: "I am not, as an operator, literally clicking through a graph... it helps to get a sense of the macro"
- The graph renderer in the PoC was ported from HCP InfraGraph — the three views (workspaces, resources, providers) and three layouts (force, stacked, radial) are validated interaction patterns
- UI-action tools from the Graph Catalog system prompt: `focus_workspace`, `show_blast_radius`, `navigate_view`, `show_provider_version` — these are the interface between the conversational agent and the graph panel
- The graph panel is supplemental: if a user never opens it, Explorer View is complete and functional without it

## Sequencing

The sub-tasks are ordered by dependency, not priority. Sub-Tasks 1 and 2 are prerequisite for everything downstream. Sub-Tasks 3, 4, and 5 can proceed in parallel once Sub-Task 1 is complete. Sub-Task 6 is the final wrap.

```
[1: Resources type card]
        |
   ┌────┴─────────────────┐
   |                      |
[2: Pre-built use cases] [3: Dependency panel]
                          |
              ┌───────────┴────────────┐
              |                        |
[4: Conversational drawer]   [5: Graph panel]
              |                        |
              └───────────┬────────────┘
                          |
              [6: Update agent reference doc]
```

## Constraints

- **D3 is prohibited** (security policy). Graph library TBD with engineering.
- **Table is always primary.** The graph panel must be opt-in. If a user never opens it, Explorer is fully functional.
- **Conversational query service is a separate workstream** (TF Partner Integrations). This plan specifies the Explorer surface contract; it does not spec the service internals.
- **ETL pipeline** (TF-2038) is a blocking dependency for Sub-Tasks 1, 3, and 5. Design can proceed; implementation waits on data availability.
- **Solace real estate** — conversational drawer must coexist with a potential Solace right panel. The drawer collapses when Solace is active; confirm exact behavior once Solace roadmap is confirmed.
- **On-prem / TFE** — all new capabilities must work within the TFE deployment model (Explorer's existing Postgres DB). No cloud-only dependencies may be introduced.

## Open Questions

- What is the conversational query service's response time target? The agent must not block the Explorer table. Should the drawer show a loading state while the agent runs, or should the table update asynchronously when the agent response arrives?
- For Sub-Task 2: which five use cases to ship first — needs PM validation (David Leeper).
- For Sub-Task 5: which graph visualization library replaces D3? Needs joint design + engineering decision before wireframes are spec'd for the graph panel.
- Does `dependency_reason: unknown` appear in the UI? Recommendation is yes (with a muted style), but this is a design decision that affects trust — if users see lots of `unknown` entries they may distrust the dependency data.
- For the graph blast-radius visual mode: what is the hop-distance color scale? Three hops? Five? Needs PRD performance target cross-reference (blast-radius analysis target: < 15 sec).
