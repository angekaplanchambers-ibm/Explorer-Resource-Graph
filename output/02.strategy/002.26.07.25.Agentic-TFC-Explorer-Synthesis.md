## TL;DR

Three initiatives are converging on the same user and the same problem surface:

- **AG-HCP** (Ange) - the agentic interaction model: trust ladder, CUJs, verified intent loop, workbench, approval gates
- **Explorer Resource Graph** (Visibility + Actions + Partner Integrations teams) - the data layer: resource inventory, dependency graph, blast-radius traversal, conversational query
- **TFC Control Center** (Gabrielle) - the global entry point: control bar, macro view, workbench UX pattern, three-level interaction architecture

Each addresses a distinct layer. None of them alone is the product. Together, they are a complete design for an agentic TFC experience: a persistent intelligent entry point (Control Center) over a verified data layer (Explorer Resource Graph) with a principled interaction model and approval governance (AG-HCP).

The central finding of this synthesis: **these three initiatives are not competing. They compose.** The design risk is that they get built in parallel and land as three disconnected surfaces. The design opportunity is to treat them as a single coherent product architecture - and design the seams explicitly.

## Where the Initiatives Align

### 1. The three-level architecture is the same

| TFC Control Center (Gabrielle) | AG-HCP Connected Experience (Ange) |
|---|---|
| Control bar - persistent entry point | Run page "Ask Terraform" + Advisor surface |
| Default / macro view - fixed panel, estate visibility | Inline explanation panel - run-page context, evidence citations |
| Workbench - full-screen, structured deep work | Workbench (Terraform Operator) - full-control, permissioned mode |

Both arrived at three depths independently: **entry -> visibility -> depth.** The language differs; the structure is identical. This is strong convergent signal. The design decision is whether to unify these into a single surface taxonomy or keep them as parallel surfaces for different entry contexts.

### 2. The design stance is the same

AG-HCP: *"The platform already holds the data the agent needs. The missing layer is product UX over it."*
TFC Control Center: *"The experience should be dehumanized by design. Trust should come from machine-state clarity, not conversational personality."*

Both documents explicitly reject chatbot metaphors. Both demand machine-state language. Both require that every result is grounded in real Terraform objects - runs, plans, policies, workspaces, state.

AG-HCP vocabulary: "verified signal", "evidence citations", "confidence labels", "audit record."
TFC Control Center vocabulary: "3 failed runs detected", "Approval required", "Checking policy results."
These are the same design principle expressed by two designers independently. Merge the vocabulary.

### 3. The workbench is the same surface

AG-HCP's workbench (Terraform Operator): full-control, permissioned, launched from inline panel or Slack pulse. Manages speculative runs, PR creation, approval gate.

TFC Control Center workbench: full-screen takeover for investigation, verification, and workflow prep. Session-based. Adaptive view by user intent.

These are the same room. They must be resolved into one surface, not two competing workbenches.

### 4. Explorer Resource Graph is the data substrate both workbenches need

AG-HCP CUJ-06 (blast-radius) explicitly requires cross-workspace dependency traversal - exactly what Explorer Resource Graph provides.
AG-HCP CUJ-01 (failed-run repair) needs evidence grounding in resource state and policy results.
TFC Control Center's macro view signals (drift, failed runs, policy failures, pending approvals) are the same signals Explorer Resource Graph surfaces.
TFC Control Center's "Inspect drift in payments workspaces" and "Prepare provider upgrade for AWS workspaces" are directly served by Explorer Resource Graph's `workspace_edges`, `workspace_providers`, and `resource_instances` tables.

Explorer Resource Graph is not a nice-to-have enrichment. It is the intelligence substrate that makes the Control Center signals accurate and the AG-HCP evidence grounding possible.

### 5. The interaction escalation model maps to the trust ladder

| TFC Control Center escalation | AG-HCP Trust Ladder |
|---|---|
| Find - navigation and lookup | L1: Explain only (read, classify) |
| Inspect - lightweight understanding | L1-L2 boundary |
| Prepare - context binding and recommendations | L2: Propose and validate |
| Execute - mutating workflows, approval required | L2-L3: Execute with human approval gate |

This is not coincidental. Both models describe progressive permission escalation through the same four moves. The TFC Control Center escalation model and the AG-HCP Trust Ladder should be documented as the same governance concept expressed at two granularities.

## Where the Initiatives Need Resolution

### Seam 1: Control bar vs. run page "Ask Terraform"

TFC Control Center's control bar is a **global persistent bottom bar** - available from any TFC page, context-agnostic at rest, context-aware when invoked.

AG-HCP's "Ask Terraform" is a **contextual trigger** - appears on the run page when a run fails, pre-loaded with run context.

These are not duplicates. They are the same entry mechanism at different specificity levels. The control bar is the ambient always-available entry. The run-page "Ask Terraform" is the contextual pre-loaded shortcut. Both should exist - the run-page shortcut should invoke the control center with run context pre-bound.

Design decision needed: does the run-page "Ask Terraform" open the Control Center macro view (pre-loaded), or does it open a dedicated inline panel? AG-HCP's current design assumes inline panel. TFC Control Center assumes the macro view. These need to converge before wireframing either surface.

### Seam 2: Bottom drawer (conversational query) vs. control bar

AG-HCP decided the conversational query for Explorer lives in a **bottom drawer**, not the right panel (reserved for Solace).

TFC Control Center's **control bar** is also a bottom-anchored entry point.

These may be the same component - or they must at minimum share the same bottom real-estate zone. If the control bar expands into the macro view and the conversational query is a bottom drawer, there is a layout conflict when both are open. This must be resolved in the layout architecture before wireframing either.

### Seam 3: The Advisor vs. the macro view

AG-HCP's **Advisor** concept: instead of a blank prompt, the agent surfaces what it can help with based on the user's current screen - derived from infrastructure state, active runs, and recent activity.

TFC Control Center's **macro view**: estate-level signals, context-aware when opened from a specific workspace or run.

These are the same concept. The Advisor is the content model for the macro view. The macro view is the container. They should be designed together: the macro view renders the Advisor's output.

### Seam 4: Sessions and audit

TFC Control Center introduces **durable sessions** - containers for infrastructure outcomes spanning multiple plans, runs, policy checks, approvals, and artifacts.

AG-HCP has **Session Bookmarks** - named milestones in an agent session, referenceable by name or event label, allowing revert and branch.

Both address the same problem: complex multi-step agentic work needs continuity, state, and recoverability. The underlying data structure may be shared. The AG-HCP audit record and the TCC session/audit layer must be designed against the same data contract.

### Seam 5: Explorer Resource Graph -> Control Center signal pipeline

The macro view's estate signals (failed runs, drift, policy failures, high-risk plans, provider upgrade opportunities) must come from somewhere. Explorer Resource Graph is the natural source for infrastructure-derived signals (drift, provider versions, blast-radius). HCP Terraform's run/policy APIs are the natural source for run-state signals. The macro view's signal pipeline needs an explicit data contract specifying which signals come from which source.

## Unified Surface Taxonomy (Proposed)

Merging the three initiatives into a single vocabulary:

| Surface | Trigger | Depth | Governance |
|---|---|---|---|
| **Control bar** | Ambient - any TFC page | Entry | None |
| **Macro view / Advisor** | Invoked from control bar or contextual shortcut | Visibility | None - read only |
| **Workbench** | From macro view or contextual entry (e.g. failed run) | Depth | Trust Ladder enforced; approval gate for writes |
| **Approval gate** | Within workbench, before any mutating action | Write boundary | Explicit human approval; L2+ only |
| **PR comment** | Created by agent; surfaces in GitHub | Async notification | No writes; links back to workbench |
| **Slack pulse** | Scheduled / event-driven | Estate digest | No writes; links to macro view or workbench |
| **MCP scope panel** | When external agent session is active | Permission boundary | Admin-configurable; read-only by default |
| **Admin audit view** | Admin settings | Retrospective | Read-only; full session + action log |

## Unified Interaction Principles (Merged)

Combining AG-HCP, TFC Control Center, and Explorer Resource Graph stances:

1. **Machine-state language** - System communicates state, not personality. "3 failed runs detected." Not "I found 3 failed runs for you." (TCC + AG-HCP, identical)

2. **Evidence before action** - Every agent response cites the Terraform objects, data, and reasoning behind it before asking for anything. A response with no cited source is a design failure. (AG-HCP Pillar 1)

3. **Structure before prose** - Cards, tables, logs, diffs, object references, and action pathways do the work. Prose clarifies but does not lead. (TCC interaction principle 3)

4. **Keep users oriented** - Users always know: where they started, what context is active, what object they are looking at, what action is available. Especially as they move between control bar -> macro view -> workbench. (TCC + AG-HCP identical)

5. **Bound actions, explicit escalation** - Entry and visibility: read-only. Depth: bounded writes (inspect, prepare, propose, resume, export). Execution: explicit human approval at the gate. No silent escalation. (TCC escalation model + AG-HCP Trust Ladder)

6. **Proactive before reactive** - The macro view / Advisor surfaces what matters before the user asks. A well-timed relevant signal earns more trust than a capable but passive assistant. (AG-HCP Pillar 4 + TCC macro view behavior)

7. **Sessions are durable** - Complex work creates a named session with checkpoints. Users can return, branch, or revert. Audit stays in HCP Terraform. (TCC sessions + AG-HCP Session Bookmarks)

## Open Questions (Consolidated)

### Architecture / convergence

- **Workbench unification**: Are the AG-HCP workbench (Terraform Operator) and the TCC workbench the same component, or do they serve different entry contexts? If one surface, which design spec leads and who owns the wireframe?
- **Control bar vs. bottom drawer layout conflict**: When the Explorer conversational query (bottom drawer) and the TCC control bar are both bottom-anchored, how does the layout resolve? Is this one component or two?
- **Macro view data contract**: Which signals come from Explorer Resource Graph APIs, and which from HCP TF run/policy APIs? Who defines this contract?

### Cross-team coordination

- **Design owner for TCC + AG-HCP convergence**: Ange owns AG-HCP surfaces. Gabrielle owns TCC. Who owns the seam - specifically the shared workbench and the control bar / run-page entry point resolution?
- **Explorer -> Control Center signal pipeline**: The PI team (conversational query) and Actions team (graph UI) need to know which macro view signals they are expected to serve. Is this in the current TF-2153 scope?
- **MCP tool exposure from Explorer catalog**: Should the catalog query tools be exposed as MCP tools so TCC can invoke graph queries directly via the external agent path? Who decides?

### Interaction model

- **Run-page "Ask Terraform" -> macro view or inline panel?** AG-HCP assumes inline panel. TCC assumes macro view. These need to converge before wireframing the run-page entry point.
- **Advisor content model**: The Advisor (AG-HCP) and the macro view content (TCC) are the same concept. Which spec leads - what signals are surfaced, in what order, at what confidence threshold?
- **Session model unification**: TCC durable sessions and AG-HCP Session Bookmarks address the same problem. Is the underlying data model shared, or will two separate session/audit stores exist?

## Recommended Next Moves

1. **Align on workbench** - Schedule a working session with Ange + Gabrielle to resolve whether the AG-HCP workbench and the TCC workbench are one surface or two. This is the highest-priority design seam.

2. **Write the macro view data contract** - Define which signals the macro view surfaces and which source provides each. Explorer Resource Graph team supplies graph-derived signals; HCP TF APIs supply run/policy signals.

3. **Journey map the control bar -> workbench flow** - A journey map tracing a user from control bar entry through macro view into workbench and back to audit covers all three initiatives in a single artifact. This is the natural next PPD pipeline step.

4. **Resolve bottom real-estate layout** - Sketch the bottom zone showing control bar, conversational query drawer, and their states (collapsed, expanded, both active). This unblocks component-level wireframing for both surfaces.

5. **PDR chain for TCC** - Gabrielle's MVP brief is detailed enough to seed a PDR-001 (architecture) for the Control Center. It should `Depends on:` AG-HCP PDR-001 (trust model) and the Explorer Resource Graph data contracts.
