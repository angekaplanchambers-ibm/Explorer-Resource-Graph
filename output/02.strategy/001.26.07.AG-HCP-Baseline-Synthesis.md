## The Core Problem

HCP Terraform has the data needed to explain and repair infrastructure failures. It has run logs, plan output, policy results, workspace state, module sources, and state. None of that is surfaced as reasoning. Users triage in isolation, dig through raw logs, and have no way to get a grounded explanation or a validated fix without manual effort.

Introducing agents creates a second layer of fragmentation risk: multiple teams are building agentic-themed features independently, without a shared interaction model. Without a unified direction, those initiatives will deliver the same inconsistent experience at the agentic layer that users already encounter today.

The AG-HCP pipeline was built to close that gap - to define the shared direction before the fragmentation compounds.

## The Vision

**Terraform Verified Signal**

Moving from a platform where failures are discovered in isolation, agentic features are built in silo, and users navigate an inconsistent experience at every layer - to one where HCP Terraform acts as a unified, proactive infrastructure engineer: surfacing risks before they become failures, proposing verified fixes grounded in the platform's own data, and giving every team and every user a consistent, trustworthy experience of what the agent can do.

## Four Strategic Design Pillars

### Pillar 1: Earn trust before asking for it
Every agent action surfaces its evidence, reasoning, and confidence level before the user is asked to approve anything. A response with no cited evidence is a design failure. Applies to: inline explanation panel, evidence panel, PR comment.

### Pillar 2: Surface the right thing, not everything
Every entry point is derived from the user's actual infrastructure state, active context, and recent history. No blank prompts. No generic capability lists. The Advisor concept operationalizes this. Applies to: run page entry, Advisor surface.

### Pillar 3: Keep humans in the driver's seat
Every write action requires explicit human approval. The approval gate is not configurable away silently. The agent reduces the effort of making a well-informed decision; it does not eliminate the decision. Applies to: approval gate, mode indicator, MCP scope panel write boundary, audit record.

### Pillar 4: Act before the user has to ask
The agent identifies risks, drift, upgrade needs, and security concerns before the user notices them. Proactive surfacing is the highest-trust action the agent can take. Applies to: workspace health indicators, blast-radius analyzer, proactive detection surfaces.

## Trust Ladder (Governance Model)

| Level | Label | What the agent does | What requires human approval | Status |
|---|---|---|---|---|
| L1 | Explain only | Classify failure, cite evidence, return structured diagnosis | Everything - no write actions | Target for regulated-environment first release (BFSI, healthcare, government) |
| L2 | Propose and validate | Explain + proposed diff + speculative run + PR draft | Merge and apply | **MVP target - confirmed by Sprint 4 Option B consensus** |
| L3 | Auto-close clean plans | As L2, but auto-closes PRs when plan is clean with no risk flags | Apply only | Near-future |
| L4 | Autonomous operate | Full autonomous within approved scope | Actions outside scope | Explicitly out of MVP scope |

Both L1 and L2 must be available at launch. Level is set per organization with optional workspace override.

## Critical User Journeys

All six CUJs follow the **Verified Intent Loop**: trigger → context assembly → diagnosis → human review → validation → approval gate → execution → audit record.

### CUJ-01 (★ Primary): Failed-run repair from run page
- **Signal strength**: Core of strategy doc; fully designed with journey map and complete PDR chain
- **Trigger**: Run fails; user lands on run page
- **Flow**: "Ask Terraform" → inline explanation with evidence → workbench → proposed diff + speculative run → PR creation + PR comment → approval → audit
- **Hard constraints**: No PR without speculative run pass AND policy pass; no apply without PR merge by human
- **Source**: [`005.26.07.01.CUJ-01-Failed-Run-Repair-JourneyMap.md`](../AG-HCP/output/02.strategy/005.26.07.01.CUJ-01-Failed-Run-Repair-JourneyMap.md)

### CUJ-02: Failed-run diagnosis from GitHub PR comment
- **Trigger**: Speculative run fails on a PR; developer sees PR comment
- **Flow**: PR comment (self-contained, actionable) → workbench link with run context pre-loaded → evidence + fix → audit
- **Key requirement**: PR comment must be usable without opening HCP Terraform

### CUJ-03: Daily Slack infra pulse - failed run triage
- **Trigger**: Scheduled analysis posts estate health summary
- **Flow**: Slack lists failed runs / drift / policy failures / upgrade risks → inline actions → write actions route to workbench
- **Key requirement**: Slack must never be a parallel control plane; audit stays in HCP Terraform

### CUJ-04: External agent using HCP Terraform context via MCP
- **Trigger**: Developer uses Claude, Copilot, or terminal agent and invokes Terraform MCP tools
- **Flow**: MCP scope panel → read within declared scope → write requires approval gate → session trace in audit view
- **Key requirement**: Scope must be visible before the session starts; admin must be able to audit any external agent session

### CUJ-05 (★ Primary): Module-backed intent to IaC
- **Signal strength**: ★★★★★ from Research Sprints 1-4 (Theme 5: Upgrade Lifecycle Toil)
- **Trigger**: User states infrastructure intent; agent maps to registry modules
- **Flow**: Module fit report → variable assignment → HCL generation → speculative run → PR with module test evidence
- **Hard constraint**: Agent must use registry modules, not raw provider resources

### CUJ-06 (★ Primary): Blast-radius visibility before a change
- **Signal strength**: ★★★★★ from Research Sprints 1-4 (Theme 1: Blast-Radius Visibility)
- **Trigger**: Module, provider, or workspace version change proposed; user needs full downstream impact
- **Flow**: Blast-radius analyzer → affected workspaces + transitive consumers → changelog-sourced breaking changes → risk annotations → human decision → audit
- **Cross-cutting note**: CUJ-06 is a shared safety check that CUJ-01 and CUJ-05 route through. Every upgrade and drift-remediation CUJ implicitly requires blast-radius analysis.

## Named Concepts

**Verified Intent Loop** - The core interaction pattern across all CUJs: trigger → context assembly → diagnosis → human review → validation → approval gate → execution → audit record. User may exit at any stage to a clean terminal state.

**Call and Response** - Structured back-and-forth between user and agent. Distinct from open-ended chat. Every response is grounded in Terraform-native context.

**The Advisor** - Instead of a blank prompt, the agent surfaces what it can currently help with on the user's active screen - derived from infrastructure state, active runs, and recent activity. User does not need to know what to ask.

**Session Bookmarks** - Named milestones in an agent session, referenceable by name, number, or event label. User or system marks checkpoints; user can revert or proceed from a checkpoint with a different approach. Addresses context degradation in long sessions.

**Trust Ladder** - The governance mechanism assigning explicit authority levels to agent workflows. Levels are assigned by users and admins, not inferred. Named as a first-class primitive in the IBM Meridian strategy.

## Connected Experience: Three Depths

The product is designed as a causal chain - each layer earns the next:

1. **Trust Signal Layer (Step 1)** - Run page inline explanation. Evidence citations, confidence labels, explainability, audit trails. Trust-earning moments at the point of highest user need. The foundation the rest of the chain is built on.

2. **Agent Interactions / Terraform Operator (Step 2)** - Current design deliverables: five CUJs, PDR chain, design compositions. Run page and PR comment are the entry-level surfaces; they connect back to Step 1 and forward to Step 3.

3. **Workbench (Step 3)** - Full-control, permissioned mode launched from within Terraform Operator. User directs the agent across a full infrastructure problem. Session Bookmarks manage complex multi-step sessions. Only reachable because trust was established at Step 1 and earned across Step 2.

These are not three separate features. They are the same verified intent loop at three depths - same interaction model, same evidence vocabulary, same trust grammar.

## Customer Voice: S. Inturi Research Quote

This quote is the anchor for the trust model and the 70-80% human-in-the-loop benchmark. It is cited directly in the Design Vision document as a primary source.

> *"The one thing I wouldn't let an AI agent do today is independently make changes to a production environment without a human reviewing and approving them first."*

> *"What would change my mind? I'd need confidence that the agent truly understands the environment, can explain its reasoning, operates within clear guardrails, and has strong auditing and rollback capabilities. Even then, I'd probably still want some level of approval for high-impact changes."*

> *"What I'd love an AI agent to do is act like a proactive infrastructure engineer. I'd love it to continuously analyze my environments, identify risks, spot drift, recommend upgrades, highlight security concerns, and tell me what I should be paying attention to before it becomes a problem."*

> *"I'd be happy for an agent to identify upgrade opportunities, update versions, rewrite configurations, run validation and Terraform plans, and open a PR with its findings. Where I draw the line is applying those changes automatically to production. The ideal setup is an agent that does 70 maybe even 80% of the work - researching, analyzing, implementing, testing, and documenting changes - while leaving the final approval to a human."*

**Design implications:**
- The 70-80% benchmark defines the MVP target: agent handles research, analysis, implementation, testing, documentation; human handles final approval.
- "Tightly scoped access" (same scoping as individual engineers) is a stated requirement, not a preference.
- "Additional insights into business promoting workflows, additional CAB reviews or production gates" - agent must understand business-layer constraints, not just technical ones.
- This quote is why the Trust Ladder stops at L3 (Prepare PR) for MVP: Inturi is comfortable with L3, not L4.

## The Connected Experience: Three-Step Causal Chain

From the Design Vision document. This describes the anti-fragmentation architecture - why the three layers must be designed as a chain, not separate features.

**Step 1: The Trust Signal Layer (run page, inline explanation)**
- Evidence citations, confidence labels, explainability, audit trails at the point of highest user need
- The only agentic entry point requiring no behavior change from the user - the failure is the trigger
- Foundation everything else is built on. Without it, Steps 2 and 3 have no credibility.

**Step 2: Agent Interactions / Terraform Operator (current design deliverables)**
- Call-and-response, Terraform Operator, Advisor, Session Bookmarks, blast-radius patterns
- Run page and PR comment are the entry surfaces; they connect back to Step 1 and forward to Step 3

**Step 3: Workbench**
- Permissioned full-control mode launched from within Terraform Operator
- User directs agent across a full infrastructure problem; Session Bookmarks manage complexity
- Only reachable because trust was established at Step 1 and earned at Step 2

**Anti-fragmentation principle:** "Workbench without the Operator is a blank interface with no trust behind it. The Operator without the run page entry is a feature users have no reason to open. Run remediation without the Operator is a dead end - a good explanation with nowhere to go."

- **The inability to set up Terraform agentically from the CLI is a stated reason to choose Spacelift instead**
- A fragmented agentic experience - multiple AI surfaces that feel like different products - will not close that gap
- A unified one will

This is the business urgency argument. The fragmentation risk is active and already affecting switching decisions.
