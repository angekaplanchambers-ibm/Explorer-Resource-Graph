# [PRD] Explorer Resource Graph: Infrastructure Visibility & Conversational Insights

**Source**: Original TF Graph Explorer PRD and Technical Graph Explorer PRD Rewrite Suggestions
**Status**: WIP
**Product**: Terraform

---

## Summary

Terraform Graph Explorer is a strategic extension of Explorer that provides organization-wide infrastructure visibility through graph-based resource, dependency, provider, module, and workspace relationships. The capability enables platform teams, cloud operators, security teams, and engineering organizations to answer infrastructure questions that are difficult or impossible to solve today without custom tooling or manual analysis. The goal is not to replace Explorer, but to extend Explorer from metadata visibility into infrastructure relationship visibility.

Explorer Resource Graph focuses on delivering read-only infrastructure intelligence built on a scalable graph ingestion architecture, PostgreSQL-backed persistence model, dependency graph analysis engine, and conversational discovery experience. The initiative establishes the technical and operational foundations required for future graph visualization, governance insights, AI-assisted exploration, and infrastructure intelligence capabilities while remaining aligned with HCP Terraform and Terraform Enterprise deployment requirements.

Explorer represents the system of record analytic cache for Terraform containing the necessary data to support a queryable semantic map of the infrastructure to be able to answer questions and the "what if" questions for humans and agents. The key is to have the full set of Terraform state data, including the dependencies to enable this capability.

## Background

Terraform customers consistently ask operational questions that cannot be easily answered today:
- How many EC2 instances of a particular type exist across all workspaces?
- Which provider versions are currently deployed?
- What resources are dependent on a specific workspace?
- What is the blast radius of a planned change?
- Which resources and workspaces consume specific modules or providers?
- What depends on this resource? What depends on this module? What workloads reach this database?
- What breaks if I destroy this VPC?
- How are workspaces connected?
- Show the full transitive closure of this resource.
- Which teams are impacted?

The Graph Catalog proof of concept demonstrated that Terraform state, plan, dependency, and provider data can be transformed into a centralized queryable graph capable of answering these questions while supporting future conversational experiences.

---

## Problem

Platform operators lack a centralized mechanism for understanding infrastructure relationships and dependencies across large Terraform estates.

As infrastructure scales, customers increasingly need:
- Cross-workspace inventory visibility
- Resource relationship mapping
- Dependency analysis
- Blast radius assessment
- Provider governance insights
- Conversational infrastructure discovery

Today, customers rely on custom tooling, manual analysis, or ad hoc state processing to answer these questions. This creates operational overhead, inconsistent results, and limits Terraform's ability to serve as the authoritative source of infrastructure intelligence.

**Current Explorer ETL limitations that require a new foundation:**
- Slow ingestion performance
- Workspace resource batching bottlenecks
- Out-of-memory risks during large updates
- Excessive asynchronous processing hops
- Limited contextual data availability
- Inability to support graph relationships
- Difficulty supporting future data domains
- Complexity scaling to enterprise deployments

- When I need to understand my Terraform estate, I want to query resources and relationships across all workspaces so that I can understand what infrastructure exists and where.

## Product Principles

**Design for Enterprise Scale** — Architecture decisions must support the largest Terraform installations without requiring future redesign.

| Metric | Target Scale |
|---|---|
| Workspaces | 800,000+ |
| Resources per workspace | 50,000+ |
| Extreme workspace size | 120,000-140,000+ |
| Total resources | 2M+ |

**Avoid Architectural Dead Ends** — All major interfaces should support additional resource types, additional data sources, future graph consumers, additional AI services, and future governance products.

**Use Proven Infrastructure** — Leverage PostgreSQL and Postgres graph extensions, existing operational tooling, existing deployment models, existing customer support patterns. Dedicated graph databases remain out of scope.

|---|---|

**Scalability** — Launch: millions of graph nodes, hundreds of thousands of workspaces, incremental synchronization. Future: multi-million resource environments, cross-region graph exploration, near real-time synchronization.

## Architecture

**Separation of concerns:**
- **Atlas**: authentication, authorization, identity management, user context
- **Explorer Resource Graph**: parsing, ETL, persistence, query execution, graph services

**Data flow:**
1. Terraform state generated
2. State parser processes artifacts
3. Shared ETL contracts publish normalized resource data
4. Graph ingestion service builds relationships
5. PostgreSQL persists graph structures
6. Query APIs expose graph intelligence
7. Explorer and conversational experiences consume results

## Phases & Requirements

### Phase 1 (Public Beta): Infrastructure Visibility Foundations

**Goal**: Establish a scalable graph ingestion and persistence architecture that enables infrastructure visibility, dependency analysis, blast radius assessment, and conversational discovery while leveraging existing Explorer infrastructure.

**Requirement 1: Dedicated ETL Pipeline Migration**
- Migrate graph ingestion from Rails-centric workflows into dedicated services
- Enterprise-scale synchronization supported
- Sensitive values redacted before persistence
- Large workspace ingestion uses staged processing
- Optimized for PostgreSQL-based storage, tabular queries, and graph queries
- Atlas remains responsible for authentication and authorization

**Requirement 2: Shared Data Ingestion Foundation** (TF Visibility + TF Actions teams)
- Shared ingestion contracts defined
- Graph-compatible resource data published
- Plan-derived dependency data available
- Single-source resource schemas where practical

**Requirement 3: Graph Persistence & Explorer Architecture** (TF Actions team owns)
- Resource relationships persisted
- Workspace dependency edges modeled
- Dependency traversal meets performance targets
- Blast-radius analysis supported
- Graph traversal via graph extensions, recursive CTEs, native PostgreSQL capabilities
- No specialized graph databases

**Requirement 4: Conversational Query Experience** (TF Partner Integrations team owns)
- Natural-language infrastructure discovery
- Responses leverage graph data
- Inventory, dependency, and blast radius queries supported
- Failed-run awareness incorporated
- Capability remains UI-agnostic

Initial conversational queries to support:
- How many EC2 instances exist across my organization?
- Which workspaces use AWS provider version 5.x?
- What resources depend on workspace X?
- What is the blast radius of workspace Y?
- Show resources using module Z.

### Phase 2 (TFC GA): Scale validation, backfill validation, operational hardening

### Phase 3 (TFE Release): Enhanced Postgres graph queries, mature operational process, reduced support burden, established backfill strategy

## Authorization Model

**Guiding principle**: Explorer will never duplicate Terraform Cloud authorization logic. Atlas remains the source of truth. Grant-based visibility model - users only access authorized resources.

**Security requirements — sensitive data must never:**
- Be persisted
- Be indexed
- Be returned in query results
- Be exposed to AI systems
- Appear in prompts

Includes: passwords, secrets, tokens, access keys. Terraform sensitivity metadata must be honored and removed throughout the ingestion pipeline.
