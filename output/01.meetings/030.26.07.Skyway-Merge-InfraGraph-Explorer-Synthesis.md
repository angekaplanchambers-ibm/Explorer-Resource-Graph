## TL;DR

Skyway began as a three-surface alignment initiative (Explorer View, TFE Search, InfraGraph). The specific merger question for InfraGraph and Explorer View was explored in a design-led workshop (March 30, 2026) and a series of design decisions documented through April 2026.

The conclusion was **not full merger** and **not continued separation**. The direction is **incremental cohesion with explicit product boundaries**: unify the journey, keep the surfaces distinct. The design language for this is: InfraGraph and Explorer View live in the same connected three-step user journey — Find/Investigate → View/Understand → Remediate/Act — but each owns a distinct leg of that journey and must not be collapsed into one generic tool.

This conclusion is now superseded by the Explorer Resource Graph initiative (see [`029.26.07.Explorer-Resource-Graph-Full-Synthesis.md`](029.26.07.Explorer-Resource-Graph-Full-Synthesis.md)), which is building the merger from the data layer up rather than the UI layer down. The Skyway work defines the product boundary logic and the interaction design principles that Explorer Resource Graph must honor.

## Origin: What Triggered Skyway

**Quote from Mary Clarke** (the trigger): *"Can we also add a thought exercise here of if it would make sense to bring these things into the same UI vs keeping them separate?"*

That question kicked off the Skyway initiative. The core framing question: **"Should InfraGraph, Explorer View, and TFE Search live under one UI?"**

The problem driving it:
- Users and internal teams cannot explain when and why to use each surface
- Overlapping workflows create cognitive load and duplication risk
- Teams were investing in adjacent problems without a shared product model
- No specific escalation forced this — it was deliberately proactive and design-led

## What Each Surface Is (as of March 2026)

### Explorer View

| Attribute | Detail |
|---|---|
| Primary job | High-level snapshot of Terraform-managed infrastructure for org-level users (admins) |
| Data scope | RUM (Terraform-managed resources) only - no unmanaged resources |
| Key capability | Fast tabular overview; governance, compliance, optimization insights; CSV export |
| Entry model | Available by default; requires Org Owner permissions; no configuration |
| On-prem | Yes - runs inside Terraform Enterprise (air-gapped environments) |
| Remediation | Observation only; users take action offline after exporting data |
| Current URL | `/app/{org}/explorer` |
| Pre-built queries | Module versions, provider versions, workspace VCS, drift, failed checks, run status |

**User actions after Explorer View**: cost management, performance evaluation, risk pattern identification (drift, outdated versions), governance and compliance decisions, chargebacks.

**Key limitation**: No historical view (only latest state). Users currently grab state files manually and compare them offline.

### InfraGraph

| Attribute | Detail |
|---|---|
| Primary job | Relationship graph and inventory across infrastructure, showing managed and unmanaged resources |
| Data scope | Both managed and unmanaged — ingests all cloud resources and infers management status from Terraform state file relationship |
| Key capability | Dependencies, lineage, blast radius; cross-product context (Terraform + Packer today); managed/unmanaged differentiation |
| Entry model | Configuration-heavy — connections must be set up manually; user triggers sync |
| Cloud support | AWS today; Azure on roadmap; GCP target; multi-cloud estate vision |
| On-prem | No. Hard boundary. Forces HTTP cloud. Cannot be used in TFE air-gapped environments. |
| Remediation | Read-only — guides users to destination tool; no actions within InfraGraph |
| Update cadence | Manual sync (July 2026); automatic updates (every 24-72 hrs) in near-future roadmap; live view (minutes delay) in GA vision |
| NL query | Natural language to query planned for July 2026 (one-shot, no chat memory initially) |

**InfraGraph's unique capability**: If an EC2 instance in the cloud has no relationship to a Terraform state file, InfraGraph concludes it is unmanaged. If a resource's dependency depends on something not managed by Terraform, it surfaces that too.

**What InfraGraph users actually prefer**: Even though InfraGraph is named for its graph, Liz Chen confirmed in the workshop: *"Many of the users we tested, they preferred a table."* The graph is useful for lineage and dependency visualization specifically; it is not the default preferred mode.

## The Overlap Map

### Where InfraGraph and Explorer View overlap

| Overlap area | Notes |
|---|---|
| Query builder | Both have or are building query capabilities |
| Top-level metadata for managed resources (RUM) | Both show managed resource metadata |
| Export data | Both can surface data for export |
| Suggested insights into management efficiency | Both serve this goal |
| Resource details with attributes | Both surface attributes |

### Where they do not overlap (hard boundaries)

| Boundary | Owner |
|---|---|
| On-prem / TFE air-gapped environments | Explorer View exclusively |
| Unmanaged resource visibility | InfraGraph exclusively |
| Resource relationships, dependencies, lineage, blast radius | InfraGraph exclusively |
| Relationships between managed and unmanaged resources | InfraGraph exclusively |

**The critical non-overlap**: Explorer View is a closed system deployed inside the customer's own TFE infrastructure. InfraGraph requires cloud connectivity. These cannot be merged at the infrastructure level without breaking TFE's deployment model.

## The Design Decisions (April 2026, evidence-grounded)

Seven decisions from the Skyway leadership one-pager, filtered to InfraGraph + Explorer View:

**Decision 1: Treat the experience as one connected 3-step journey.**
Find/Investigate → View/Understand → Remediate/Act. Both surfaces participate in this journey; neither owns all three steps alone.

**Decision 2: Keep specialized end states distinct while improving cross-surface cohesion.**
Explorer View = admin overview (managed posture). InfraGraph = relationship analysis (dependency context, blast radius). These roles must not collapse into a generic tool.

**Decision 3: Preserve Explorer View as high-level managed (RUM-only) posture; InfraGraph as deep relationship context across managed and unmanaged.**
This is the primary boundary. Violating it creates duplication and confusion.

**Decision 4: Sequence entry as Insight → Decide → Navigate.**
Users see organization performance first, then are guided to InfraGraph, Explorer View, or Search+Import based on what the insight indicates. InfraGraph's dependency/blast-radius value should be visible at the portfolio level before users drill in.

**Decision 5: Strengthen cross-surface discoverability through a single entry narrative and predictable handoffs.**
The primary failure mode was: *"Which tool should I use right now?"* The fix is not to merge the tools but to make the next destination explicit at each handoff point.

**Decision 6: Prioritize clarity and reduced cognitive load over full merger aesthetics.**
Unification that does not materially improve user clarity is not justified. "Do nothing" is a valid outcome.

**Decision 7 (IA):** Two IA options were evaluated:
- **Option A (Org-First)**: Org Dashboard → Explorer View, Workspace, InfraGraph, IAM, Settings side by side
- **Option B (Workspace-Centric)**: Org → Workspaces → Explorer View, InfraGraph, Search, Import, IAM, Settings

Option B was preferred because it avoids a new multi-org dashboard layer and stays closer to the existing Terraform mental model.

## What the Wireframes Encoded

The Storybook wireframe decisions that directly reflect the InfraGraph + Explorer View merger logic:

| Wireframe decision | What it implements |
|---|---|
| Explicit surface-boundary guidance on Organization Overview for Explorer View, Resource Graph, and Search+Import | Users see which surface is for managed posture, which for relationship analysis, which for import — at the page level, not just in docs |
| Cross-organization relationship insights surfaced on Organizations Portfolio | InfraGraph's dependency/blast-radius value is visible before users decide whether to open InfraGraph |
| Embedded compact Visibility section in Organizations Portfolio (query tile, top-five types, tabbed suggested questions, Saved Views) | Previews the Visibility/Explorer View experience at the portfolio level - reinforces one mental model at two scales |
| Concrete handoff deep-links replacing abstract labels | Context is preserved when moving from Explorer View → InfraGraph or the reverse; no context reconstruction on arrival |
| Removed standalone source-freshness panel | Added scanning cost without improving decision flow - cognitive load reduction over visual completeness |

## What Remained Unresolved (March–April 2026)

The workshop explicitly did not produce a full unification decision. These were left open:

- **Who owns the "final decision"** on InfraGraph + Explorer merger? The workshop was advisory, not authoritative.
- **Historical context**: Explorer View users want it; InfraGraph has it on the roadmap (temporal data for observability portfolio). Not in near-term scope for either.
- **NL query convergence**: Both surfaces are building natural-language query capabilities independently. A unified query entry point was floated but not decided.
- **Agentic overlay**: How agentic experiences (Solace, conversational query) sit across InfraGraph and Explorer View was not addressed in the Skyway work.
- **InfraGraph on TFE**: Confirmed impossible without breaking the air-gap model. This means any "unified" experience in TFE environments is Explorer View only, with InfraGraph absent. No workaround was proposed.

## Connection to Explorer Resource Graph (Current Initiative)

The Skyway Merge work defined the **why** and the **product boundary logic**. The Explorer Resource Graph initiative (late July 2026) is executing the **how** from the data layer up.

| Skyway established | Explorer Resource Graph implements |
|---|---|
| InfraGraph's unique value: blast radius, cross-workspace dependency traversal, relationship modeling | Blast-radius API (recursive CTE on `workspace_edges`), dependency closure per resource instance |
| Explorer View's unique value: managed-resource metadata, on-prem/TFE support, tabular speed | Existing Explorer PostgreSQL datastore extended with attribute values and dependency data |
| Shared data foundation needed | New ETL pipeline (TF-2038, Alex Redinger): state parser → Explorer DB direct push |
| Grant-based authorization (Atlas as source of truth) | Grant system (short-lived UUID, Redis TTL, Postgres workspace scoping) |
| Table-first, graph as context | Design direction confirmed by Ange + Chris 1:1 (July 22, 2026) |
| LLM-driven UI manipulation as primary agentic capability | Chat tool-calling loop with UI-action tools (`show_blast_radius`, `focus_workspace`) |
| "Do not ship Graph Catalog" / adopt ideas not the product | Three-team delivery model building the ideas into Explorer, not a standalone service |

**Key gap Skyway did not solve that Explorer Resource Graph now must**: InfraGraph is not on-prem. The Explorer Resource Graph initiative uses Explorer's existing TFE database. This means Explorer Resource Graph can eventually deliver InfraGraph-style dependency intelligence inside air-gapped TFE — which InfraGraph itself could never do.

## Strategic Position (Director memo, April 23, 2026)

From [`010.26.04.23.Skyway-Director-Strategic-Memo.md`](../../Skyway-Merge/Skyway-Merge/output/010.26.04.23.Skyway-Director-Strategic-Memo.md):

> *"The most important question is not 'Can these products be combined?' It is 'What level of cohesion materially improves user clarity, adoption, and action quality without destroying product focus?'"*

The recommended direction: **incremental cohesion with explicit product boundaries.**

In practical terms:
- One shared journey model across surfaces
- Clearer role definition for each surface
- Stronger handoffs and context carryover
- Shared language and wayfinding patterns
- No forced full merger unless evidence shows merger improves user outcomes

## Open Questions (still live as of Explorer Resource Graph initiative)

- **InfraGraph's organizational future**: Leadership is still deciding whether InfraGraph remains Terraform-focused or evolves into a broader unified knowledge graph (UKG) spanning infrastructure, applications, and configuration. Chris Arcand's position: Terraform's graph needs can be solved without InfraGraph, and should be.
- **Who arbitrates the product boundary** between Explorer Resource Graph and InfraGraph once ERG has blast-radius and dependency intelligence? Is InfraGraph superseded for Terraform-native use cases?
- **TFE on-prem path**: Explorer Resource Graph can deliver InfraGraph-style capabilities inside TFE (air-gapped). Does this effectively make InfraGraph's TFE story moot?
- **NL / conversational query unification**: InfraGraph planned one-shot NL query for July 2026. Explorer Resource Graph's TF Partner Integrations team is building a full conversational query service. Do these converge or remain separate?
- **Agentic handoff**: The Skyway design work predates the AG-HCP agentic pipeline (CUJ-06 blast-radius, CUJ-01 evidence grounding) and the Explorer Resource Graph initiative. The blast-radius surface designed in Skyway wireframes needs to be reconciled with the agent-driven blast-radius flows in the PDR chain.
