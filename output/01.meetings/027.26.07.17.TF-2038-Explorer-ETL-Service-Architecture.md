## Background

Resource Visibility work revealed that the existing ETL does not scale to the profile of the massive data transfers that come with frequent, large resource updates. Add to that, reliance on Workspace Resources hampers Explorer's ability to expand the scope of Resource Visibility. We need a way to get more resource data and move it faster.

The PoC work done by Chris Arcand for Graph Catalog revealed what is understood as a better path to collect resource data. The big challenge now is translating the takeaways of the PoC work into enterprise software.

---

## Problem

No new user-facing problems are addressed in this work. See the Resource Visibility PRD for more in-depth specifications. All requirements stated in this document explicitly assume that product support for and parity with existing Resource Visibility functionality will be maintained.

**Technical problems:**
- Existing Explorer ETL scaling is not up to the demands of Resource Visibility
- Current ETL is too slow for the massive amount of resource updates
- Current ETL is prone to OOM when handling too many resources at once, leading to batching and subsequent ETL slow-downs
- Current ETL struggles with tracking larger workloads
- Future goals of supplying more information about resources (attributes, blast radius, drift details) depend on an ETL with more context than we get by consuming Workspace Resource records

---

## Phase 1 Requirements

**Goal**: Resource Visibility in Explorer is fed by a scalable, performant ETL that meets the needs of future scope expansion.

**Data compatibility**
- Data collected from the service must meet the needs of existing Resource Visibility data expectations
- This includes Provider and Module data not present in the PoC demo

**Bulk update support**
- Need to be able to ETL without a single-record-at-a-time producer/consumer pattern
- While individual resources are rationalized as records, updates are typically monolithic — need an efficient, reliable bulk update option
- Bonus: rationalize and send only diffs of data, or only process diffs as input into Explorer

**Direct artifact reading**
- Read directly from run artifacts in an efficient manner, both for small and large sets of resources
- We want maximal context, not second-hand summary data

**Performance targets**
- P95 size workspaces must reasonably update in under ~30 seconds
- Very large workspaces can be slower (define the JPMC largest size), but target under an hour

**State version consistency**
- Workspace references to the current state version must stay in sync with reported resources
- Example: Workspace State Version A → Resource Set A; updates process; Workspace State Version B → Resource Set B. At no point will Workspace State Version A → Resource Set B

**Zero-disruption**
- Must not interrupt TFC or TFE to spin this up or run it

**Backfill support**
- Support on-demand (single-workspace) and rebuild-the-world (all of TFC/TFE) styles of backfill
- A single workspace must be able to resend data to the service
- The entire installation needs to be able to request reloading data

**Reliability**
- The job must be fault-tolerant and retry on failure
- Customers expect near-real-time data reflected in Explorer
- All resources must be represented in Explorer — records updates may have latency, but updates must not fail to reach Explorer

**Extensibility**
- Be able to extend this solution to other data types (graph data, policies, Stacks, etc.) in the future
- The service/ingestion architecture should not be dictated solely by the short-term needs of Resource Visibility
- New job types for new data types and additional information on existing types (drift updates, graphing) must be definable

---

## Rejected Requirements

- **Workspace in-progress marker**: When a resource job is sent to the service, marking the related workspace record in Explorer as "awaiting updates." Rejected as adding complexity without sufficient validation that it is needed. Could be revisited for very large workspaces where the delay might cause user confusion.
