# 022. Terraform Graph Catalog — PoC Synthesis

## TL;DR

The `terraform-graph-catalog` is a standalone Go proof-of-concept by Chris Arcand (arcand@ibm.com) that solves a problem HCP Terraform has had for years: you cannot ask it cross-workspace questions about your infrastructure estate. The service maintains a queryable index of every resource instance, provider configuration, and cross-workspace dependency edge across an organization. It has a recursive blast-radius query, keyset-paginated REST API, and an LLM chat layer backed by any OpenAI-compatible endpoint - with the LLM also able to drive the visual graph UI.

The author is explicit: **this is a PoC, not a production service.** The name is temporary ("don't even call it 'graph catalog' in the roadmap slides"). The architecture and ETL interfaces are what matter. Call it Explorer V2 if you want.

The memo explicitly names **Skyway** as a parallel effort from the design org pulling on the same threads, and says these efforts should be combined or one done over the other. The memo also cites **Structured State (TF-707)** and **tf-state-lab** as prior art that was never fully prioritized.

## Key Discussion Points

### 0. The author's strategic framing (IBM Think opinion paper, March 2026)

The author's stated view - explicitly described as "the opposite strategy from Meridian" - is that read-only introspection is the low-hanging fruit of the agentic era:

> "Any initiative aimed at cloud visibility or resource mapping must treat the agent as the primary consumer. Instead of building shiny dashboards for human eyes, we build queryable, semantic 'maps' of the infrastructure state. An agent should be able to traverse a complex graph of Terraform-managed resources to answer 'What will break if I change this?' faster and more accurately than any human looking at a monitoring tab."

The author's sequencing argument: start with better introspection at lower stakes ("It's generally ok if your robot makes a mistake counting your EC2 instances. It's definitely not ok if your robot brings down the platform deleting a database"), then build change management on top. The PoC is intended to demonstrate this approach is tractable without waiting for InfraGraph alignment.

### 1. The problem this PoC is responding to

Three longstanding unsolved customer requirements that have been deferred because of scope confusion between Explorer, InfraGraph, and Meridian:

- **Cross-workspace inventory** - "Which workspaces use the AWS provider at version 5.x?", "How many S3 buckets does our org have?", "Show me all resources in project X with tag Y"
- **Dependency impact** - "Which resources depend on `aws_vpc.main`?", "If workspace `ws-network-prod` changes, which downstream workspaces are in its blast radius?"
- **Estate opaqueness at scale** - The Explorer feature exists but lacks attribute values, dependency closure, and cross-workspace edges. Progress has been misaligned for years.

The author's position: "The fact that you cannot simply ask HCP Terraform 'How many xlarge EC2 instances do I have across all the workspaces in my organization?' with a good visual is concerning. This is very basic functionality that I'd expect to have seen 3-6 months ago."

### 2. What the service does

Two query classes + one agentic interface:

**Cross-workspace inventory**
- Filter resource instances by type, org, project, exact attribute values
- Filter provider configurations by source, version constraint, or exact version
- Keyset paginated, returns exact total count across all matches

**Dependency impact**
- `GET /api/v1/grants/{grant_id}/resources/{address}/dependents` - Resources that depend on a given address, annotated with `dependency_reason` (explicit / implicit:<attribute> / unknown)
- `GET /api/v1/grants/{grant_id}/workspaces/{id}/blast-radius` - Resources in all workspaces that directly or transitively consume a workspace's outputs via `terraform_remote_state`, annotated with `hop_distance`

**LLM chat over the catalog** (dev-only)
- Tool-calling loop (up to 6 iterations) against catalog query tools
- Tools: `list_workspaces`, `list_resources`, `get_dependents`, `get_blast_radius`, `list_providers`
- UI-action tools: `focus_workspace`, `show_blast_radius`, `navigate_view`, `show_provider_version` - the LLM drives the visual graph in the browser
- Returns: model's final answer + transparency log of every tool call (`tool_calls` array) + UI actions to execute
- Backed by any OpenAI-compatible endpoint (was Copilot proxy; now GitHub Models or OpenAI recommended)

### 3. Named competitor: StateGraph

The author explicitly mentions StateGraph as a competitive prompt for this work: "AI has lowered the barrier to entry for competitors to maintain their own Terraform runtimes which can adhere to the specification and bring interesting capabilities that actually are quite compelling. StateGraph is one example." This PoC is partly a market investigation of what StateGraph is doing and whether Terraform can close that gap from within.

### 4. Architecture: the Janus pattern

Standalone Go service, own Postgres DB, own Redis, no gRPC yet. Communicates via HTTP with shared secrets.

```
terraform-state-parser --[ingest secret]--> POST /ingest/state-version
Atlas (plan config + edges) --[service secret]--> POST /ingest/plan
Atlas --[service secret]--> POST /api/v1/grants --> grant_id (TTL in Redis)
caller / LLM agent --> GET /api/v1/grants/{grant_id}/... (scoped to grant)
```

Two secrets:
- **Ingest secret**: used by `terraform-state-parser` for state ingest
- **Service secret**: used by Atlas for plan ingest, provider version patch, and grant creation

**Grant system** (the most architecturally distinctive part): Atlas evaluates permissions using its own policy layer, then exchanges that decision for a short-lived UUID grant scoped to a set of workspace IDs. The catalog has no concept of users, orgs, or projects as access-control keys. Grants are stored in Postgres (workspace membership for SQL scoping) and Redis (TTL / liveness check). Redis is authoritative for expiry.

### 5. Data model (six tables)

| Table | What it stores |
|---|---|
| `resource_instances` | One row per resource instance per current state version. Full JSONB attributes (sensitive values replaced with `"<sensitive>"`), full transitive dependency closure as a Postgres array. |
| `resource_configs` | Plan-derived config metadata: attribute expression references, explicit `depends_on`. Powers `dependency_reason` annotation. |
| `workspace_providers` | Provider configurations from plan JSON: source, alias, version constraint, resolved version (patched separately after apply). |
| `workspace_edges` | Directed cross-workspace dependency edges (consumer, producer) from `terraform_remote_state` data sources. Atlas resolves names to IDs before sending. Foundation of blast-radius traversal. |
| `state_outputs` | Root outputs; sensitive output values nulled out. |
| `access_grants` / `access_grant_workspaces` | Grant records and workspace membership sets. |

### 6. Blast-radius implementation

Recursive CTE on `workspace_edges` with:
- Per-path cycle guard (tracks visited workspace IDs in a Postgres array)
- Hop cap of 32 (safety bound; real graphs are typically 1-3 hops)
- Collapsed to minimum hop distance per workspace via `GROUP BY` before joining resource instances
- Returns all resource instances in downstream workspaces annotated with `hop_distance`

This is a native SQL query. No graph database. No external dependency.

### 7. Dev UI

Single-page app (vanilla JS + D3) embedded in the binary via `go:embed`. Three views:
- **Workspaces**: nodes are workspaces, edges are cross-workspace dependencies
- **Resources**: all resource instances in a selected workspace as a DAG
- **Providers**: bipartite graph of providers and workspaces

Three layout algorithms (force, stacked, radial). Color-coding by resource category. Graph renderer was ported from the HCP InfraGraph project. Chat panel in the sidebar. LLM drives graph highlighting via UI-action tools.

**Not for production**: unauthenticated, requires `GRAPH_CATALOG_DEV_UI=true` flag.

### 8. Explorer vs. Graph Catalog

| Dimension | Explorer | Graph Catalog |
|---|---|---|
| Deployment | Rails engine inside Atlas monolith | Standalone Go service |
| Ingest | ActiveRecord hooks → Sidekiq (7+ async hops) | Atlas / state-parser HTTP POST (2-3 hops) |
| Attributes per resource | Name, address, type, provider, module only | Full JSONB attribute values (sensitive redacted) |
| Dependency closure | Not modeled | Full transitive closure per instance |
| Cross-workspace edges | Not modeled | Explicit `workspace_edges` table |
| Blast radius | Not possible | Native recursive CTE |
| LLM interface | None | Tool-calling chat loop |
| What Explorer has that Catalog lacks | Workspace operational metadata (drift counts, health checks, VCS associations, tags, versions), bulk actions, saved views, CSV export | - |

**Author's recommendation**: Treat the two systems as complementary for now. Explorer owns operational metadata. Graph Catalog owns the dependency graph and attribute-level index. The longer-term question is whether Graph Catalog eventually replaces Explorer or becomes Explorer V2.

## Author's three non-negotiable design principles

These were intentional and the author explicitly says to preserve them:

1. **Scale is everything.** Must handle thousands of workspaces and resources. Everything must be paginated, limited, and performant. JPMC (largest TFE customer) must be able to use it.
2. **Monolithic decomposition is a central principle.** Own service, own database, clear ETL interface. Authorization is grant-style to leave Atlas as the source of truth. Create explicit interfaces.
3. **The queryable state must be presumed sanitized.** Sensitive values are replaced at parse time - never in the catalog. LLMs must never see sensitive values. This is a design invariant, not a runtime check.

## Production Readiness Gaps (from author)

| Gap | Severity | Notes |
|---|---|---|
| Telemetry is a no-op | Critical | Metrics abstraction writes to a blackhole sink. No Datadog traces, no latency histograms. Service cannot be operated. |
| Redis is load-bearing for all queries | High | Redis outage takes down every query endpoint. Decision needed: fallback to Postgres `expires_at` when Redis unreachable? |
| No rate limiting | High | Ingest endpoints have no rate control. Large ingest can cause Postgres contention. |
| Ingest does not scale to large workspaces | High | Large JSON bodies (potentially 500 MB+ plan files) POSTed directly. `PlanPayloadBuilder` loads entire plan JSON into Sidekiq worker memory. DELETE + INSERT transaction holds a lock proportional to workspace size. Needs chunked/streamed approach. |
| Atlas integration is PoC-only | High | Three integration points (plan ingest, provider version patch, grant creation) are not implemented in production Atlas. All three need to be Sidekiq jobs for durable retries. |
| `terraform-state-parser` fanout missing | High | State parser needs additional fanout to catalog ingest endpoint. Not implemented. |
| Missed pushes = stale data | Medium | No polling, no reconciliation loop, no backfill. Integration layer must compensate with durable retried delivery. |
| Plan and state can get out of sync | Medium | Plan data and state data ingest independently. `dependency_reason` annotations can be stale or absent after a workspace change or failed apply. |
| No secrets rotation | Medium | Both secrets are static env vars. Rotation requires service restart. |
| No readiness/liveness split | Low | Single `/healthz` for both. Transient DB hiccup triggers container restart. |
| `make seed` is a stub | Low | No tooling to load synthetic test data. Dev requires manually triggering real ingest or writing a seed script. |
| Inference API is hand-waved | High | LLM chat uses a local Copilot proxy for the demo. Any production agent feature needs a proper inference API — especially for TFE, which may need a configurable inference endpoint for air-gapped environments. |

## Open Questions

- **What is Skyway?** The memo references it as a design org effort with wireframing that "does not seem to be starting from the same angle that this catalog does" but with "the broad idea of consolidating concepts of IG, Explorer, and LLM flows" being similar. Is this the same initiative as the Terraform Verified Signal design work in AG-HCP? -- design org
- **InfraGraph vs. Graph Catalog for Terraform-native graph data?** The author is explicit that "avoiding progress by convincing ourselves there's scary overlap between product offerings" cannot continue. Is InfraGraph still the intended destination, or does this replace it for Terraform-native use cases?
- **Should Graph Catalog use the existing Explorer logical database** (same Postgres instance, separate schema) rather than its own DB? The author recommends investigating this.
- **What does Structured State (TF-707, tf-state-lab) have that is relevant?** Prior art that was never fully prioritized.
- **For TFE: does the inference API need to be customer-configurable?** The author flags this as not a small scope question - especially for air-gapped environments.
- **Should the chat tool-calling loop be exposed as MCP tools** in addition to the OpenAI tool-calling interface? This would make the catalog directly consumable by external agents (e.g. through the Terraform MCP Server).
