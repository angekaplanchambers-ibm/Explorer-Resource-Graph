## TL;DR

Explorer Resource Graph is the product name for what started as the Graph Catalog PoC. It is being built by three teams in parallel under a multi-team H2 delivery framework with a HashiConf deadline. The initiative extends HCP Terraform's existing Explorer feature from metadata visibility into full infrastructure relationship and dependency intelligence. The core bet: Terraform already has all the state and configuration data needed - the missing piece is a scalable ETL, a graph query layer, and a conversational interface over it.

The design direction is settled: **table-first, graph as context, LLM-driven UI manipulation as the distinguishing capability.** Do not ship a standalone graph product. Adopt the ideas from the Graph Catalog PoC, not the PoC itself.

---

## What This Initiative Is

**Explorer answers**: "What Terraform assets exist?"
**Explorer Resource Graph answers**: "How is my infrastructure connected?"

Explorer Resource Graph is a read-only infrastructure intelligence layer built on top of Explorer's existing PostgreSQL datastore. It enables customers - and agents - to answer questions about cross-workspace dependencies, blast radius, provider versions, resource attributes, and module consumption that are currently impossible without custom tooling.

Explorer is positioned as **the system of record analytic cache for Terraform** - the authoritative infrastructure relationship system for both HCP Terraform and TFE.

---

## Origin: From Graph Catalog PoC to Product

The Graph Catalog PoC (Chris Arcand, ~2 days of AI-assisted development, July 2026) demonstrated that Terraform's existing v4 state and plan artifacts are sufficient to build:
- Cross-workspace resource and provider inventory with full JSONB attributes
- Dependency traversal with annotated dependency reasons
- Recursive blast-radius analysis via cross-workspace edges
- An LLM chat layer that queries the catalog AND drives the graph visualization

**Chris's explicit message**: "Don't ship Graph Catalog. Take these ideas and incorporate them well into the product."

**Ange and Chris's 1:1 alignment (July 22)** - four key decisions:
1. D3 cannot be used (security risk) - graph visualization needs a different library
2. Explorer View stays **table-first** - graph is a secondary context supplement, like a code editor minimap
3. **LLM-driven UI manipulation** is the most valuable concept to adopt from the demo
4. Conversational query will live in a **bottom drawer**, not a right panel (to coexist with Solace)

---

## Design Direction (settled)

**Keep**: Explorer View's proven metadata-table foundation, CSV export, comparison workflows, query/filter experience.

**Add**:
- LLM manipulation of the UI (conversational query featurette, bottom drawer entry point)
- Natural language as the query generation trigger
- Context-aware graph manipulation (focus, filter, highlight, navigate based on user request)
- Graph visualization as a secondary supplement: blast radius, dependency context, relationship orientation
- Table + graph dual experience - table prominent, graph contextual

**Leave behind**:
- Standalone graph visualization product
- Graph as a primary experience
- D3 codebase
- Deep graph enrichment beyond what Explorer View currently offers

## What the Data Layer Provides

Six tables (from Graph Catalog PoC schema, inherited by Explorer Resource Graph):

| Data | What it answers |
|---|---|
| `resource_instances` (full JSONB attributes, dependency closure) | "How many xlarge EC2s across all workspaces?", "What attributes does this resource have?" |
| `resource_configs` (plan-derived expression references, `depends_on`) | "Is this dependency explicit or implicit through an attribute reference?" |
| `workspace_providers` (source, version constraint, exact version) | "Which workspaces use AWS provider 5.x?" |
| `workspace_edges` (consumer → producer, from `terraform_remote_state`) | "What consumes outputs from this workspace?" |
| `state_outputs` (root outputs, sensitive values nulled) | "What does this workspace export?" |
| `access_grants` (grant ID → workspace set, Redis TTL) | Authorization scoping - Atlas evaluates permissions, issues a short-lived grant |

**Security invariant**: Sensitive values are replaced at parse time with the literal `"<sensitive>"`. They never reach the catalog, are never indexed, and are never passed to an LLM.

## ETL Architecture (TF-2038, Alex Redinger)

**Problem with current Explorer ETL:**
- Too slow for large resource updates
- OOM-prone during batching
- 7+ async hops (ActiveRecord after_commit hooks → Sidekiq)
- No attribute values, no dependency closure, no cross-workspace edges
- Cannot support graph data or future data types

**Target ETL:**
- Direct reading from run artifacts (state, plan) - maximal context, not second-hand summary data
- Bulk update support - not single-record-at-a-time
- Idempotent on state version ID
- Fault-tolerant with durable retries (Sidekiq jobs, not fire-and-forget)
- On-demand (single workspace) and rebuild-the-world (full TFC/TFE) backfill
- State version / resource set consistency guaranteed (no mismatched pairs)
- Extensible to other data types: policies, Stacks, drift data, graph edges

**Reference model**: The Archivist handoff approach Atlas already uses for state-parser.

## Conversational Query: Key Design Decisions

- **Not UI-specific in Phase 1** - capability is built as a standalone service; can converge with Explorer chat or other surfaces later
- **Not competing with Explorer chat** - treated as separate from where it lives
- **Bottom drawer placement** (not right panel) - right panel reserved for Solace
- **Solace coexistence** - if Solace (IBM's agentic front-end framework, like a VS Code right-panel agent) is eventually embedded in Terraform, conversational query must share real estate without conflict
- **SLM for query generation** - the SLM builds the query and manipulates the UI; not a general-purpose chat assistant

Initial supported questions:
- How many EC2 instances exist across my organization?
- Which workspaces use AWS provider version 5.x?
- What resources depend on workspace X?
- What is the blast radius of workspace Y?
- Show resources using module Z.
- What's the blast radius of this resource?

## Authorization Model (inherited from Graph Catalog)

Atlas evaluates permissions → issues short-lived grant (UUID, workspace-scoped, Redis TTL).
Explorer Resource Graph has no concept of users, organizations, or projects as access-control keys.
Grant stored in two places: Redis (liveness/TTL) and Postgres (workspace membership for SQL scoping).
Redis is the authoritative expiry signal. Every query checks Redis first.

**Principle**: Explorer will never duplicate Terraform Cloud authorization logic. Atlas remains the source of truth.

---

## What This Is Not

- Not a standalone graph visualization product
- Not a replacement for InfraGraph (though it may eventually be for Terraform-native graph data)
- Not an agentic workflow or change management system (read-only in Phase 1)
- Not dependent on a dedicated graph database (Postgres + recursive CTEs only)
- Not a competing surface to Solace or Explorer chat

## Open Questions

- **InfraGraph vs. Explorer Resource Graph** - Chris Arcand's position: Terraform has its own graph needs independent of InfraGraph's broader vision. Leadership is still deciding InfraGraph's direction. Does Explorer Resource Graph supersede InfraGraph for Terraform-native use cases, or do they eventually interoperate?
- **Solace integration specifics** - Ange confirmed Solace is on the roadmap as a right-panel agent experience. What is the exact product timeline, and does it affect Phase 1 conversational query placement?
- **Graph library selection** - D3 is ruled out (security). What replaces it for the graph visualization component?
- **Inference API for TFE** - Any LLM-backed conversational query for TFE needs a configurable inference endpoint (customer bring-your-own for air-gapped environments). Is this in Phase 1 scope or deferred?
- **MCP tool exposure** - Should the catalog query tools be exposed as MCP tools so external agents (including the Terraform MCP Server) can call the graph catalog directly?
- **Failed-run conversational experience** - TF-2153 references "TF-Failed-Run Investigation: A First Conversational Experience for Terraform" as a Partner Integrations deliverable. How does this relate to CUJ-01 (failed-run repair) in the AG-HCP agentic pipeline? Are these the same workstream?
- **Explorer Resource Graph ↔ AG-HCP agentic pipeline** - The AG-HCP strategy (CUJ-06, blast-radius; CUJ-01, evidence grounding) requires exactly the data this service provides. Who coordinates the design/API contract between these two initiatives?
